# Incident Runbook: Abuse Wave & Hostile Burst Defense

| Metadata | Details |
|---|---|
| **Incident ID** | `RUNBOOK-OPS-08-ABUSE` |
| **Requirements** | SRS `OPS-08`, `ABUSE-01`..`06`, `SEC-01`..`10` |
| **Severity Level** | SEV-2 (High Automated Load) / SEV-1 (Coordinated Distributed Attack) |
| **Subsystem** | Abuse Engine, Moderation Queue (M11), Rate Limiter, Kill Switches |

---

## 1. Trigger Conditions & Detection

1. **Abuse Cluster Alert Fired**: An owner alert with kind `ABUSE_CLUSTER` is generated by the Abuse engine.
2. **Elevated PoW Failure Rate**: Proof-of-work challenge failure rate exceeds 40% across incoming requests.
3. **Single IP / Subnet Spike**: More than 100 requests per minute generated from a single IP hash or small address cluster.
4. **Hostile Content Detection**: Repeated attempts to upload malicious file formats (e.g. Windows PE binaries `MZ`, Linux `ELF`, zip-bombs, script tags in text files).

---

## 2. Automated Defensive Shielding

The workspace implements layered defenses that activate automatically:
- **Proof-of-Work (PoW) Escalation**: Client devices with Trust Level 0 or high burst rates receive SHA-256 difficulty challenges, raising the computational cost of attacks without affecting human users.
- **Magic-Byte Sniffing & Safe File Rejection**: Content sniffing rejects executable headers, polyglots, and script files at the gateway before parsing (`FILE-01`, `FILE-06`).
- **CSV Formula Injection Sanitization**: Prepends `'` to leading `=,+,-,@` characters to prevent spreadsheet code execution (`FILE-07`).
- **Per-IP & Per-User Rate Limiting**: Excess requests encounter immediate HTTP 429 `RATE_LIMITED`.

---

## 3. Triage & Incident Investigation

### Step 1: Inspect Moderation Queue & Alerts (Control Center M11)
- Navigate to `/admin` ➔ Moderation Queue.
- Review recent flagged events, challenge failure counts, and IP hashes.
- Inspect pattern:
  - Is the attack targeting Chat completion, File uploads, or Authentication endpoints?

### Step 2: Query Abuse Tables in Database
```sql
SELECT source_key, trust_level, count(*) as admissions_count
FROM abuse_admissions
WHERE created_at > CURRENT_TIMESTAMP - INTERVAL '15 minutes'
GROUP BY source_key, trust_level
ORDER BY admissions_count DESC LIMIT 10;
```

## 4. Active Mitigation Measures

### Measure 1: Ban or Restrict Abusive User Accounts (Control Center M5)
For targeted attacks originating from specific accounts:
```http
POST /admin/api/users/{userId}/moderate
Content-Type: application/json
X-CSRF-Token: {csrfToken}

{
  "action": "ban",
  "reason": "Automated script flood violating AUP Section 4"
}
```

### Measure 2: Escalate Global Proof-of-Work Difficulty
If the attack uses rotating IP proxies:
1. Increase baseline challenge difficulty from 4 to 8 via Control Center or runtime options.
2. Legitimate browsers will solve the challenge in 200–400 ms, while high-frequency bot nets will experience prohibitive CPU costs.

### Measure 3: Activate Hierarchical Kill Switches (Emergency Defense)
If an attack threatens server stability or storage capacity, use Control Center M2 to toggle specific kill switches:
- **`file_uploads`**: Immediately stops all file ingestion while keeping text chat alive.
- **`signups`**: Freezes new account creation during registration floods.
- **`free_tier`**: Pauses anonymous or free-tier admissions.
- **`all_ai`**: Emergency master cutoff (returns clean 503 to all requests).

---

## 5. Recovery & Post-Mortem

- Confirm attack traffic has subsided and challenge success rates have normalized (> 95%).
- Re-enable any temporarily suspended kill switches.
- De-escalate PoW difficulty to default levels.
- Update abuse detection rules and IP hash blacklist if necessary.
